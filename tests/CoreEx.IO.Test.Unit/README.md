# CoreEx.IO contract and migration baseline

Steps 1 through 5 cover format-neutral contract invariants, extension-point behavior, executable flat/hierarchical CSV processing with CsvHelper 34.0.0, finite input/group limits, and strict encoding/BOM behavior. Fixture integrity tests remain distinct from runtime evidence; processor tests prove parsing, whole-file acceptance, routing/assembly, stream ownership, unit scopes, and hook orchestration.

## Portable fixtures

`Fixtures/baseline.json` records required `ValidateThenExecute` outcomes under `CollectErrors`, using UTF-8 without a BOM and LF endings. Flat files have a column-name header and typed fields `Id` (integer), `Name` (string), and `Quantity` (integer; `NotNull`, not `Mandatory`, so zero is valid). Their CSV header is not a data record.

Hierarchical fixtures are positional and have exact, case-sensitive discriminator values: `H` is a single required header, `O` a root order, `L` a required contiguous child of an order, and `T` a single required final trailer. Each order requires at least one line. The trailer carries root count and sum of line quantities. Header/trailer records count as physical records, not execution units. The orphan and unknown record in `orders-invalid-structure.csv` are diagnostic failures, not contributors to accepted order totals.

Flat records begin on physical lines 2 and 3 even when the second record spans two lines. The final flat conversion failure and hierarchical trailer mismatch both require zero execution calls. EOF reconciliation anchors to the last record's physical starting line; logical child/property paths never imply physical coordinates. The manifest is a migration acceptance baseline, not a claim that every behavior already exists in the source demo.

## Source characterization

The reviewed source is `C:\Repos\Playground\Sor.Demo`. Its unit solution `Sor.Demo.Test.Unit.slnf` passed 423 generator tests and 196 sample unit tests during the design review. Its Aspire/transport runtime tests were not run. The useful starting coverage includes `CsvProcessingTest`, `OrderExecutionTest`, `BuilderExtensionsTest`, `GenerationTest`, `GeneratedRulesTest`, `MultiRecordGenerationTest`, `HierarchyConfigurationTest`, `OnRampMapCompatibilityTest`, and `ProjectBatchTest`. Keep generated-project compilation coverage during migration; string comparisons alone are insufficient.

| Area | Source behavior or dependency | Migration action |
|---|---|---|
| Parser | The demo uses TinyCsvParser 3.0.11 synchronously; its async path retained record terminators in final fields, mishandled malformed final quoting, and swallowed mapping faults. | Replaced with CsvHelper 34.0.0 low-level parsing. Malformed-record callbacks become current-record diagnostics; recovered malformed rows never reach business validation/execution. |
| Parser compatibility | CsvHelper 34.0.0 is a fresh rewrite, strong-named, licensed MS-PL OR Apache-2.0, with dependency-free net8.0/net10.0 runtime assets. | Keep version-specific regression coverage. Decode through a strict StreamReader because its native UTF-8 path silently accepted malformed bytes despite a strict Encoding option. Step 5 verifies all three frameworks, strong-name loading, matching/conflicting Unicode BOMs, and strict byte decoding. |
| CodeGen API | Demo pins OnRamp 2.4.0; CoreEx pins 2.3.1. Demo uses CodeGenPropertyMap, PrepareMapAsync, and MapEntryKey. | Upgrade deliberately in Step 6 and run RefData/Count regressions; do not copy source against incompatible APIs now. |
| Expected errors | Demo validation flattens errors into strings and keeps a file-wide list. | Preserve localization/severity/location in individual diagnostics; do not construct ValidationException or Result.ValidationError per bad record. |
| Input ownership | Demo has path, stream snapshot, and revision-pinned Blob APIs. | Core only accepts a stream-opening factory; caller guarantees immutable bytes, processor owns returned streams, and there is no compulsory snapshot. |
| Execution | Demo has hierarchical validation/replay support. | Give flat input the same whole-file and EOF acceptance barrier; fresh models/context on replay. |
| Lifetimes | Multi-record registrations share CsvFileProcessor&lt;CsvRecordEnvelope&gt;; first registration wins. Handlers are singletons. | Distinct generated service identities; fresh scoped handlers per row/root group; never share tracked services across a file. |
| CoreEx ambient context | Resolving the current scoped registration resets/disposes its parent. | Add safe nesting in Step 2 before implementing unit execution; saving/restoring a disposed reference is not sufficient. |

The runtime acceptance matrix in `docs/file-processing-design.md` remains authoritative for the larger suite: headers/selectors, quoting, conversions, requiredness, record policies, missing records, EOF reconciliation, no-write validation, report failures/backpressure, replay/ownership/cancellation, bounds/encoding, context isolation, multi-definition registration, and concurrent invocations. Numeric limits and BOM handling are CoreEx-owned policies, not assumed parser defaults.

## Flat runtime evidence

`CsvFileProcessorTests` exercises late mapping and EOF rejection with zero execution, fresh models/context/scopes on replay, original Result failure, scoped errors/warnings and CoreEx validator messages, case-insensitive/reordered/duplicate/missing headers, positional selectors, missing fields, multiple errors per record, comments/blanks, quoted/escaped/multiline fields, CR/LF/CRLF locations, single-byte nonseekable async input, split Unicode, invalid UTF-8, invariant nullable/date conversion, and concurrent invocation mapping/counters.

Lifecycle coverage includes cancellation before opening, during blocked validation/replay reads, and inside a scoped diagnostic callback; open/read/converter/business/reporting faults; null/unreadable streams; replay count/mapping drift; invalid replay contexts; missing execution handlers; awaited report backpressure under the file ambient context; scope disposal; and asynchronous disposal of every owned input. Test streams reject synchronous reads. Separate 10K conversion-error and malformed-quote cases assert zero observed first-chance exceptions during processing, and streamed diagnostic tests retain no history in framework state.

## Hierarchical runtime evidence

`CsvHierarchyFileProcessorTests` processes all three order fixtures and proves zero writes for a late trailer mismatch or structural rejection. Coverage includes exact/missing/unknown discriminators, malformed-record isolation, recognized-invalid counts, accepted envelope availability and duplicate preservation, first/last rules, orphan children, arbitrary nested assembly and physical provenance, sibling-order/reopening failures, and `Many`/`One`/`Optional`/`OneOrMore` cardinality at parent and file level.

Lifecycle coverage includes fresh replay wire records/context/envelopes, field validation only on the first pass, one async handler scope per root and pass with parent restoration, root-policy group errors without fake invalid physical rows, route-specific continuation for mapping/missing-child failures, required-record/parent/EOF anchors, EOF reconciliation, original execution Result failure, count/mapping replay drift, projection/reporting faults, awaited reporting and cancellation under the file ambient context, context-reuse rejection, and invalid named route mappings before opening input.

Independent keyed hierarchy definitions sharing a group CLR type coexist with a flat definition, using their own scoped handlers under concurrent replay in either registration order. Weak-reference evidence checks that completed projected groups, aggregate nodes, and wire records are not retained by file state. A 10K bad-child conversion case explicitly allows 10,001 group records (root plus children) and asserts zero observed first-chance exceptions.

## Bounds and compatibility evidence

`CsvBoundsAndEncodingTests` covers exact and one-byte-over input limits (including 1–3-byte prefix budgets), finite defaults, group root/descendant counting and reset, invalid/unknown/malformed descendants, terminal rejection despite collect/route policies, no partial-group/EOF completion, zero execution/replay on rejection, and operational faults for replay bound/encoding drift. Oversized unclosed quoted input reads at most its configured budget plus one and emits a limit diagnostic without first-chance exceptions. Cancellation interrupts the exact-boundary EOF probe and disposes input.

UTF-8, UTF-16 LE/BE, and UTF-32 LE/BE are exercised with and without matching BOMs on single-byte nonseekable streams, including split non-ASCII/supplementary text. Cases cover conflicting BOMs, partial UTF-8 signatures, empty/BOM-only input, embedded U+FEFF preservation, named-header and hierarchy-discriminator BOM handling, BOM-inclusive byte counts, strict replacement-fallback override without mutating caller encodings, malformed/truncated code units, and ASCII repertoire violations. Invalid encoding now produces terminal content rejection rather than the Step 3 decoder exception escaping. The .NET decoder still throws internally; no zero-exception encoding claim is made.

The representative workload case reports cumulative allocation and elapsed time (not peak/live memory or a performance assertion) for 100,000 flat 64-character rows with scoped validation and a 10,000-record root with 1,024-character children. Local net10 Debug observations were approximately 222 MB and 57 MB allocated respectively, supporting explicit configurable budgets of 64 MiB input and 10,000 group records, not a claim that source bytes equal heap usage. Tests verify strong-name tokens for both assemblies. Run the entire project with `dotnet test tests\CoreEx.IO.Test.Unit\CoreEx.IO.Test.Unit.csproj --configuration Debug -p:CoreExLocalTargetFramework=` to exercise net8/net9/net10.
