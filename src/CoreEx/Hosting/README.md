# CoreEx.Hosting

> Provides base classes for timer-driven and synchronized hosted services, `HostSettings` for standardized host configuration, and `WorkOrchestrator` for tracking long-running distributed work state with pluggable storage.

## Overview

`CoreEx.Hosting` addresses three distinct but related concerns: running background work reliably within an .NET hosted-service model, protecting a push/callback-driven processor (an external SDK owns the delivery loop, not a timer we control) from a sustained run of failures, and tracking the state of long-running distributed operations that outlive a single request or host invocation.

The hosted service base classes (`TimerHostedServiceBase`, `SynchronizedTimerHostedServiceBase`) provide a consistent foundation for background polling workers — handling pause/resume, error-interval back-off, no-op mode for tests, DI-scoped execution, and health check integration via `HostedServiceHealthCheck`. Synchronized execution uses renewable, owned leases through `ISynchronizer`; coordination scope and failure guarantees depend on the registered provider, and leases do not provide fencing or an exactly-once guarantee. `CircuitBreakerResiliency<TOwner>`/`RetryResiliency<TOwner>` are for the *other* shape of hosted service — one that doesn't drive its own poll loop (e.g. an Azure Service Bus `ServiceBusProcessor` or a Cosmos DB Change Feed Processor keeps calling the handler regardless of failure) - self-pausing/self-resuming (circuit breaker) or retrying a caller-classified subset of failures (retry), for any owner that exposes pause/resume semantics. `HostSettings` standardizes how a host, including ASP.NET Core, exposes its solution name, domain name, environment, and source URI to the rest of the application.

`WorkOrchestrator` tracks explicitly managed long-running work items (for example async job processing, background import, or an orchestration hand-off). Each item has a `WorkState` record persisted via a pluggable `IWorkProvider`, with Created → Started → Indeterminate → Completed/Failed, or Expired/Canceled states and automatic expiry. Every item is identified by an operation name and a `CompositeKey` instance identifier, qualified by the host `IHostSettings.DomainName` and, when present, the ambient `ExecutionContext.TenantId`. `WorkState` persists the domain, tenant, operation name and instance ID directly. Creation is insert-if-absent; transitions use provider ETag compare-and-set and return `WorkTransitionResult` so callers can distinguish Applied, LeaseHeld, LeaseLost, Expired, AlreadyFinished, and other outcomes. A finished state is never overwritten.

## Key capabilities

- ⏱️ **Timer hosted service**: `TimerHostedServiceBase` runs `OnExecuteAsync` on a configurable interval with randomized first-start staggering, error back-off interval, and pause-on-exception support.
- 🔒 **Synchronized timer hosted service**: `SynchronizedTimerHostedServiceBase` wraps `TimerHostedServiceBase` with a renewable, owned `ISynchronizer` lease to coordinate execution across host replicas. Lease expiry, backend failure, or a paused process can still permit overlap; correctness-critical resources need fencing or transactional ownership checks.
- ♥ **Health check integration**: `HostedServiceHealthCheck` reports `ServiceStatus` as a named health check entry; `HostedServiceManager` aggregates multiple service statuses for a single health endpoint.
- ⚙️ **Host settings**: `HostSettings` standardizes solution name, domain name, environment name, and source URI — read from `IConfiguration` or provided explicitly — for use by caching, event naming, and logging.
- 📋 **Work orchestration**: `WorkOrchestrator` manages create, lease start/takeover/renewal, progress, completion, failure, cancellation, and fencing for long-running work items.
- 🗄️ **Work providers**: `InMemoryWorkProvider` (process-local; `AddInMemoryWorkProvider`) for development, tests and single-instance hosts; `CoreEx.Redis`'s `RedisWorkProvider` (`AddRedisWorkProvider`) for shared state across instances. Provider reads include their clock time; Redis uses server `TIME` by default, while InMemory uses `TimeProvider`.
- 🔗 **Synchronization leases**: `ISynchronizer` acquires renewable, owned leases used by `SynchronizedTimerHostedServiceBase` to coordinate execution across host replicas. Lease loss cannot prevent uncooperative work from continuing, so correctness-critical resources need fencing or transactional ownership checks.
- 🛡️ **Self-pausing circuit breaker**: `CircuitBreakerResiliency<TOwner>.Create(...)` builds a Polly `ResiliencePipeline<Result>` that pauses (with exponential backoff) then self-resumes any owner exposing pause/resume methods, once a sustained failure ratio is observed - for a push/callback-driven processor where an external SDK owns the delivery loop (an ASP.NET Core hosted service can't otherwise control its own retry cadence the way `TimerHostedServiceBase` can). Originally implemented for `CoreEx.Azure.Messaging.ServiceBus`'s `ServiceBusReceiverBase`, promoted here so `CoreEx.Cosmos`'s Change Feed Processor-based outbox relay (and any future processor with the same shape) shares the exact same behaviour.
- 🔁 **Classified-failure retry**: `RetryResiliency<TOwner>.Create(shouldHandle, ...)` builds a bounded retry-with-backoff pipeline for a caller-supplied subset of failures (no "retry everything" default - unlike the circuit breaker, blindly retrying an unclassified failure risks retrying one retrying can never fix). Promoted alongside the circuit breaker for the same reason.
- 🔑 **Shared owner-context plumbing**: `ResilienceOwner<TOwner>` flows an owning instance through a Polly `ResilienceContext` so `CircuitBreakerResiliency<TOwner>`/`RetryResiliency<TOwner>` callbacks can resolve it back out (`PropertyKey`/`GetOwner`) - the plumbing both share, split out since it isn't circuit-breaker- or retry-specific.

## Work guarantees and usage

Identify work with a stable operation name and a `CompositeKey`; the instance ID is `CompositeKey.ToCanonicalString()`, so a single-component key equals its string value and a stored instance ID can be replayed with `CompositeKey.Create(instanceId)`. The canonical instance ID must not be empty or whitespace. The orchestrator qualifies the identity with the host domain and the ambient `ExecutionContext.TenantId`: a present tenant is an explicit isolation boundary (tenant-scoped), otherwise the work is domain-wide. Callers that retry or deduplicate the same logical operation must supply the same name and key, and every processing host must establish the same tenant in its `ExecutionContext` (the published message carries it). A key is an identity, not authorization; its storage representation depends on the provider.

`ISynchronizer` and `IIdempotencyStore` take the same name-and-key shape with the same domain/tenant qualification; each purpose uses its own namespace. A synchronized timer derives its lease name from the service type and name; its lease is domain-wide by default and tenant-scoped if its execution context is configured with a tenant. See the [Redis guide](../../CoreEx.Redis/README.md#breaking-migration-and-rollout) before switching existing callers.

```csharp
var args = WorkArgs.Create<CatalogImport>("catalog-import", CompositeKey.Create(importId));
var created = await workOrchestrator.CreateAsync(args, cancellationToken).ConfigureAwait(false);
```

`WorkOrchestrator.StartAsync(operationName, key, leaseOwner)` returns a `WorkTransitionResult` containing an applied `WorkLease` with the work identity, owner token and epoch. Rejected transitions report a `WorkTransitionOutcome`; `ToResult()` converts them to `NotFoundException`, `ConflictException`, or `ConcurrencyException` with a `WorkTransitionErrorCodes` value as `ErrorCode` (for example, `work-lease-held` versus `work-expired`). These codes are distinct from the persisted `WorkErrorCodes` describing a failed, canceled, or expired operation. Every worker-owned update requires that lease; after a takeover, stale epochs cannot renew, report progress, complete, fail, or release the operation. Work transitions are linearized by ETag compare-and-set, but handler execution is not: a slow, paused, or disconnected worker may continue after its lease expires while a redelivery has already taken over. A caller that detects lease renewal loss can only request cooperative cancellation. Handlers that need protection against overlapping side effects must use the exposed work identity and lease epoch to fence their own writes.

In an at-least-once delivery system, the engine maintains at most one unexpired lease per operation; it does not provide exactly-once execution or fence business side effects. Redis failover can lose acknowledged transitions because replication is asynchronous; this is an accepted risk that CoreEx does not mitigate. A write timeout throws `WorkOutcomeUnknownException`; a missing record never proves that work did not run.

All work timestamps and deadline comparisons use provider time, not the request's frozen `ExecutionContext.Timestamp`. InMemory uses its `TimeProvider`. Redis reads server `TIME` by default; `RedisWorkProviderOptions.TimeProvider` is an explicit test/deterministic-scenario override and should not be used in a multi-host production deployment unless the clocks are controlled. Redis key TTL still elapses in real Redis time.

The work store contains operation metadata only, never result payloads. Persist results in the owning domain's store and set `ResourceLocation` on completion to an app-relative URI such as `/products/123`; absolute and protocol-relative redirect targets are rejected. Ownership defaults to the current execution user, or `AuthenticationUser.EnvironmentUser` if no execution context exists; an explicit `WorkArgs.User` takes precedence. Hosts sharing an environment identity are indistinguishable as owners, so specify an appropriate caller identity when isolation matters. Anonymous-created operations have no owner and are visible to any caller, so use an unguessable instance ID where the key is exposed to untrusted callers. Otherwise, caller-facing status access requires an execution context with an equal authenticated owner; `AuthenticationUser` record equality includes `UserName`, so supply stable values. `GetAsync` is an unchecked system/worker API.

Unfinished `IWorkProvider` records are retained until the later of `ExpiryOn` and the current lease expiry, plus `Retention`. Once work finishes, the deadline no longer applies: the record is retained for `Retention` from the finishing write, extended to `StartBy` plus `Retention` when `StartBy` is later, so a fenced record outlives any late first delivery. Early-completed work is therefore not retained until `ExpiryOn`. Configure retention to cover the broker's message TTL and maximum redelivery window. A subscriber integration must handle missing records explicitly because absence is not evidence that the handler never ran.

`WorkOrchestratorOptions` reads `CoreEx:Hosting:Work:Expiry`, `Retention`, `LeaseDuration`, `MaxExecutionAttempts`, and `StartTimeout`; constructor-supplied options override these defaults. The Redis DI registration requires the Redis operation timeout multiplied by three to fit within the configured lease duration.
